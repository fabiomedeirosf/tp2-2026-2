2 · O cardápio da Sabor & Café

A cafeteria vende bebidas simples, cada uma com seu preço individual:

Bebida simplesPreço
CaféR$ 5,00
CháR$ 4,00
Suco de laranjaR$ 6,00

Mas os clientes também pedem bebidas compostas — feitas de uma bebida base somada aos ingredientes adicionais:

Bebida compostaComposiçãoPreço
CapuccinoCafé + Leite + ChocolateR$ 8,00
MochaCafé + ChocolateR$ 6,50
Chá com LeiteChá + LeiteR$ 5,50
Regra de negócio: o preço de uma bebida composta é a soma do preço da bebida base com o preço de cada ingrediente adicional.

3 · A tentativa óbvia: calcular o custo "na mão"

Uma primeira reação do programador é mapear cada combinação:

public double calcularCusto(Bebida b) {
    if (b == CAFE)             return 5.00;
    if (b == CHA)              return 4.00;
    if (b == CAPUCCINO)        return 5.00 + 1.50 + 1.50;
    if (b == MOCHA)            return 5.00 + 1.50;
    // ... dezenas de mais if/else
}

E quando o cliente pedir "capuccino sem chocolate, com chantilly extra"?

  • Cada nova combinação exige um novo ramo no código (ou uma nova constante).
  • O caixa não pode montar o pedido em tempo de execução.
  • A descrição da bebida fica espalhada em outro cascade de ifs.

4 · Tentativa por herança: por que não escala

A solução "clássica" de POO seria criar uma subclasse para cada combinação:

public class Capuccino extends Cafe { ... }
public class CapuccinoComChantilly extends Capuccino { ... }
public class Mocha extends Cafe { ... }

  • Combinatória: cada novo ingrediente × cada bebida base = novas subclasses.
  • O método getCusto() é duplicado em toda subclasse.
  • Remover um ingrediente exige outra subclasse (CapuccinoSemChocolate?).

5 · Intenção do Decorator (GoF)

Intenção: "Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality."
— Gamma et al., Design Patterns, 1994

Traduzindo para a Sabor & Café:

  • Compor objetos: cada pedido é uma cadeia bebida base + adicional₁ + adicional₂ …
  • O comportamento (getCusto(), getDescricao()) emerge da soma recursiva da cadeia — não de ifs nem de subclasses.
  • Novos adicionais são novas classes pequenas, abertas para extensão, fechadas para modificação.

Para o capuccino:

capuccino.getCusto()
  = chocolate.getCusto()   // 1.50 + base
  = leite.getCusto() + 1.50 // 5.00 + 1.50 + 1.50
  = cafe.getCusto() + 1.50
  = 5.00 + 1.50 + 1.50 = 8.00

6 · Analogia: cada adicional é um envelope

O cliente pediu um capuccino com chantilly. Imagine "embrulhar" o café:

Chantilly( Chocolate( Leite( Café ) ) )

No mundo físico

  • Começa com a xícara de Café.
  • Uma camada de Leite envolve o café.
  • Uma camada de Chocolate envolve o conjunto.
  • Por fim, a camada de Chantilly.

No objeto

  • Cada camada guarda uma referência à bebida que ela decora (a "base").
  • Ao calcular o custo, cada camada delega + soma seu extra.
  • Fora para dentro: descrição e custo se constroem recursivamente.

Decorator = "envelopar" um objeto com uma ou mais camadas que estendem seu comportamento.

8 · Participantes e colaborações

Papel GoFClasse na aulaResponsabilidade
ComponentBebida Define a interface comum (custo e descrição) para componentes e decoradores.
ConcreteComponentCafe, Cha Objetos "de verdade" que podem ser decorados; implementam o comportamento base.
DecoratorAdicional Mantém uma referência (base) a um Bebida e delega as chamadas a ele.
ConcreteDecoratorLeite, Chocolate, Chantilly Adicionam comportamento (custo extra, nome) antes/depois da delegação.

Colaboração: como o custo encadeia

Chocolate.getCusto() → Leite.getCusto() → Cafe.getCusto() → 5.00 → volta somando +1.50 → +1.50 → R$ 8,00

Nenhum participante precisa saber a composição completa: cada camada só conhece a sua base. O cliente monta a cadeia desejada em tempo de execução.

9 · Código Java (1/3) — Component e ConcreteComponents

A interface comum: Bebida

public interface Bebida {
    String getDescricao();
    double getCusto();
}

Bebidas simples

public class Cafe implements Bebida {
    public String getDescricao() { return "Café"; }
    public double getCusto()      { return 5.00; }
}

public class Cha implements Bebida {
    public String getDescricao() { return "Chá"; }
    public double getCusto()      { return 4.00; }
}

Qualquer bebida que o caixa queira vender sozinha implementa Bebida — e nada mais.

10 · Código Java (2/3) — O decorator abstrato

Adicional implementa Bebida e guarda a bebida que está decorando. Isso é o truque do padrão: decorador é também um componente, então pode ser decorado de novo.

public abstract class Adicional implements Bebida {
    protected Bebida base;

    public Adicional(Bebida base) {
        this.base = base;
    }

    // delegação: a descrição da base + o nome do extra
    public String getDescricao() {
        return base.getDescricao() + " com " + getNome();
    }

    protected abstract String getNome();

    // por padrão, só repassa o custo da base
    public double getCusto() {
        return base.getCusto();
    }
}

11 · Código Java (3/3) — Decorators concretos e cliente

public class Leite extends Adicional {
    public Leite(Bebida base) { super(base); }
    protected String getNome() { return "Leite"; }
    public double getCusto()   { return base.getCusto() + 1.50; }
}

public class Chocolate extends Adicional {
    public Chocolate(Bebida base) { super(base); }
    protected String getNome() { return "Chocolate"; }
    public double getCusto()   { return base.getCusto() + 1.50; }
}

public class Chantilly extends Adicional {
    public Chantilly(Bebida base) { super(base); }
    protected String getNome() { return "Chantilly"; }
    public double getCusto()   { return base.getCusto() + 1.00; }
}

O cliente (caixa) monta o pedido em tempo de execução

// capuccino = Café + Leite + Chocolate
Bebida capuccino = new Chocolate(new Leite(new Cafe()));
System.out.println(capuccino.getDescricao());
// >> Café com Leite com Chocolate
System.out.printf("R$ %.2f%n", capuccino.getCusto());
// >> R$ 8,00

// outro pedido: capuccino leve, com chantilly no lugar do chocolate
Bebida leve = new Chantilly(new Leite(new Cafe()));
System.out.printf("%s — R$ %.2f%n", leve.getDescricao(), leve.getCusto());
// >> Café com Leite com Chantilly — R$ 7,50

12 · Consequências (prós e contras)

✔ Vantagens

  • Responsabilidade única: cada adicional é uma classe pequena e focada (só o extra).
  • Aberto/fechado: novos adicionais sem tocar no código existente.
  • Combinações em tempo de execução: o cliente constrói a cadeia que quiser, na ordem que quiser.
  • Evita classes "fat": sem explosão de subclasses CafeComLeiteComChocolateComChantilly.

✘ Cuidados

  • Muitos objetos pequenos — pode poluir depuradores e toString/identidade.
  • A ordem importa: Chocolate(Leite(Café)) ≠ Leite(Chocolate(Café)) na descrição (no custo, neste exemplo, é igual).
  • Configuração manual: montar a cadeia à mão fica verbosa; factories podem ajudar.
  • instanceof/getClass() sobre decorators é frágil (ex.: "é um Café?" pode ser não, é um Chocolate envolvendo um Café).

13 · Implementação: decorator transparente vs. opaco

TransparenteOpaco (o da aula)
Decorator subclasse do componente (ex.: Adicional extends Cafe) implementa só a interface do componente
Identidade capuccino instanceof Cafe → true capuccino instanceof Cafe → false (é Chocolate)
Risco transparência quebrada: o decorator "é" o componente em testes, mas não deve ser usado sozinho cliente precisa sempre tratar como Bebida, nunca como tipo concreto
GoF recomenda Aceitar a interface do componente e não adicionar métodos novos no decorator — assim o cliente ignora a camada e o encapsulamento se mantém. Decorators "self-decoration" (decorator que decora outro decorator) são naturais: nossa cadeia Chocolate(Leite(Café)) é exatamente isso.

No UML do GoF, a ligação Decorator → Component aparece com "…" indicando que o decorator é um componente estendido.

14 · Padrões relacionados e resumo

PadrãoDiferença-chave
Adapter Muda a interface de um objeto; Decorator mantém a interface e muda o comportamento.
Strategy Troca o algoritmo inteiro; Decorator acrescenta camadas ao comportamento existente.
Composite Também usa composição recursiva, mas com foco em estrutura (parte-todo); Decorator foca em comportamento e na ordem das camadas.

Levando para casa

  • Decorator = composição dinâmica no lugar de hierarquia de subclasses.
  • Cada adicional da Sabor & Café é uma camada que delega + soma.
  • Component, Decorator e ConcreteComponent compartilham a mesma interface — é isso que permite empilhar.
